# CLAUDE.md (admin)

Admin panel for gallery.sksat.net. This is a separate Qwik/QwikCity project under `admin/` with its own `package.json`, `node_modules`, and Cloudflare Pages deployment. Read alongside the root [CLAUDE.md](../CLAUDE.md) — workflow rules, fixture conventions, and VRT baseline policy are inherited from there. Code shared with the public gallery lives in `../shared/` (`@shared/*`, plain TS; see the root CLAUDE.md): e.g. `shared/overlay/` gives the edit page's full-screen preview (`src/components/photo-preview.tsx`) the same look and progressive loading as the gallery's photo overlay.

## Differences from the root project

- **Dev port**: `5175` (root uses `5174` for Playwright). Avoids conflicts when both projects' dev servers are running.
- **Routing**: `/` dashboard, `/media/` + `/media/[id]/` (photo metadata), `/tag/` (tags), `/setting/` (site settings) + `/setting/upload-rule/` (upload rules), `/camera/` + `/camera/new/` + `/camera/[id]/` (camera records; route paths are singular, except the mass noun `/media/`), `/calendar/` (`[...date]`: the newest month with photos, `/calendar/<yyyy>/` the year shaded by count, `/calendar/<yyyy>/<mm>/` a month with each day's first photo, count and the visibility icons of its photos; every listed photo, private ones too, by the date part of its timestamp, whatever its public taken_at level; counting shared with the public calendar in `../shared/calendar/`, `src/lib/calendar.ts`). A day, month or year opens `/media/?date=YYYY[-MM[-DD]]`; the list, the Files view and the edit page's prev/next filter on it (`TAKEN_ON_SQL`: a range on the raw `timestamp` string, whose date part is already the photo's local date, so it is exact and stays on `idx_media_live_timestamp`); a calendar page counts only its month or year in SQL (`loadMonth` / `loadYear`: one grouped range read, the covers as its bare columns, and one index step each for the neighbouring months or years), and it shows as a chip (also from `sm` up, where the form has no field for it). `/map/`: every listed photo with a position, private ones too, at its saved position (`src/components/admin-map.tsx`: DOM markers merged per zoom with the shared `clusterByGrid`, a popup per place with each photo's visibility and a link to its edit page, and the list under the map for the keyboard). The maps load MapLibre GL JS only from their visible tasks (`src/lib/map.ts`), with OpenFreeMap's positron or dark style after the theme (see the root CLAUDE.md for the choice); E2E stubs those styles and refuses any other external request (`e2e/map-helpers.ts`), and VRT hides the WebGL canvas. E2E/VRT data comes from `e2e/fixture.sql`. Links from the list to an edit page carry the list URL in `?back=` (`mediaEditHref` / `safeBackHref` in `src/lib/format.ts`); the edit page's "← Media" returns there and its ‹ 前へ / 次へ › step through that list (`src/lib/neighbors.ts`). Its unsaved-changes guard uses `usePreventNavigate$`, which is experimental and enabled in `vite.config.ts`. A tap on the edit page's photo opens a full-screen viewer (`src/components/photo-preview.tsx`, `?fs=1` while open) for going through a batch: ←/→ or a swipe step through the same list as 前へ/次へ (←/→ also on the page when no field has focus, and a horizontal swipe on the page's photo, not the form; neither while 反映 or a save of the photo is running), and 1/2/3 or its buttons only mark the photo's new visibility as pending (`src/lib/review-pending.ts`, kept in `sessionStorage` per list) and go on to the next photo; a bar (in the viewer above the buttons on phones, top right from `sm`; on the page while it is closed) counts them by level and applies them all at once with 反映 (`useApplyPending`, the bulk update in chunks of 100; photos that become public or unlisted are shown as thumbnails first) or drops them with 破棄, and 元に戻す reverts the whole batch (`useUndoPending`). Pending choices trigger the leave guard except when stepping to another photo. Key handling is in `src/lib/review-keys.ts` (no shortcuts while typing, composing or with modifiers; 1/2/3 not on key repeat). 反映 waits while the form has unsaved edits. "← Media" adds `#m-<id>`, and the list scrolls that photo into view. On phones the `/media` filter form sits in a `<dialog>` opened with `showModal()` as a bottom sheet (a `<noscript>` style shows it inline without JS), and its selects apply as soon as they change; from `sm` up the same dialog is styled inline and the Filter button applies (a closed select fires `change` on every arrow-key step). Filters on `/media` apply in place (client-side navigation), so any `<Link>` there whose href depends on the query is keyed by its href: Qwik City's `Link` keeps the href it was first rendered with while the route stays the same.
- **Cameras**: table names are singular (`camera`, `camera_image`; `media` is a mass noun). A photo links to at most one `camera` row via `media.camera_id` (migration `0002_camera.sql`, which replaced the old free-text `camera_make`/`camera_model` columns). The camera row is the single source of truth: it has `manufacturer` / `manufacturer_url` (kept on the camera for now; a `manufacturer` table once several cameras share one) and `model`. Cameras have no delete yet; the FK has no `ON DELETE`, so a camera with photos cannot be removed by SQL either. Pictures of a camera live in `camera_image` (`ON DELETE CASCADE`, ordered by `position`, unique per camera + file); `file` is a bucket path validated by `validateImageFile`; on the camera page a bare file name means `/camera/<slug>/<name>` (`resolveCameraImagePath`). Camera pictures have no upload (photo uploads cannot target `/camera`), so the file is placed in B2 by hand. Removing a picture can be undone from the toast (`restoreCameraImage` puts it back at its old index in one D1 batch). The camera page also lists the photos taken with it (`src/components/camera-photos.tsx`, `listCameraPhotos`, newest first, each linking to its edit page); ticked ones lose the camera with カメラを外す (`useRemoveCameraPhotos`, only rows that have this camera, 100 per request, the camera then `manual` so the reader does not link it again; undo through `useRestoreCameraPhotos`). The length limit of a bare name counts the prefix (`cameraImagePathLengthError`, checked in the browser and by the action).
- **Visibility and public ids** (migration `0003_visibility.sql`): `media.visibility` is `private` (default for new rows; admin only), `unlisted` (opens by URL, never listed) or `public`. `media.public_id` is the photo's id in public URLs (`/photo/<public_id>/`): 10 symbols from `23456789abcdefghjkmnpqrstuvwxyz`, set once at creation and never changed (triggers fill it in when an INSERT leaves it out and reject any change; a migration that rebuilds `media` must recreate them). App code generates it with `generatePublicId()` (`src/lib/public-id.ts`, `crypto.getRandomValues`); the trigger's `random()` is only a fallback for raw SQL. Visibility is set on the edit page or in bulk from `/media` (tick rows → Apply; at most one page, 100 ids; on phones a selection bar fixed at the bottom). The bulk action returns each changed row's previous visibility, and the toast's 「元に戻す」 sends it back through `useRestoreVisibility`. The API lists only `public` rows.
- **Upload status and folders** (migration `0004_upload.sql`): `media.status` is `uploading` (row created to reserve the path; the file may not be in the bucket yet) or `ready` (default, so existing and hand-inserted rows are ready). Only `ready` rows are photos: the admin's lists, Files view, prev/next and camera counts, and every API Worker query filter on it. `media.size` / `sha256` (unique, NULL for old rows) / `uploaded_at` are filled by uploads. Folders are implicit (built from `media.file`, `src/lib/folders.ts`) plus rows in `folder` (`path` like `/VRChat/2026-11`, unique) so that a folder created in the Files view exists while empty; empty folders are shown only when no filter is set. Folder names: 1–64 of `[A-Za-z0-9._-]` (trimmed, not starting with `.`), at most 8 deep and 200 chars (`validateFolderName` / `validateFolderPath`); the same characters as bucket paths, which go into URLs unescaped.
- **Moving, renaming and the trash**: moving or renaming a photo or folder rewrites only `media.path` (and `folder` rows under it) in one D1 batch (`moveItems`, `src/lib/db-ops.ts`; plans in `src/lib/file-ops.ts`); the B2 key never changes. A name that is taken is refused. The edit page moves/renames the photo (場所と名前) and sends it to the trash; the Files view renames the open folder or sends it to the trash (its photos are trashed, its folder rows removed; unfinished uploads stay listed as incomplete). The photo UPDATE first parks moved rows at `/.tmp/<id>` so swaps and chains do not trip the unique index halfway; a photo is never placed under a path that is a photo. Each can be undone from the toast. The Files view's contents are a multi-select listbox (`src/components/file-browser.tsx`, tiles or a list with name / date / size / visibility / platform columns, sorted by 名前 / 撮影日 / 追加日 (row id) / サイズ either way; the choice is kept per viewer in `localStorage` `admin-files-view`; `src/lib/file-view.ts`). Items are selected like in a desktop file manager (the tick mark, Shift range, Ctrl/Cmd toggle, Ctrl/Cmd+A, Esc; once something is selected a click toggles; a reload of the same folder and filter keeps every selected key, even one it briefly lacks, and only the selected items shown are counted and acted on, `reconcileSelection`; `src/lib/selection.ts`); one tab stop (roving tabindex): arrows move the focus (Shift extends), Space picks, Enter opens, F2 renames (`useRenameItem`), Delete trashes; a right click, Shift+F10 or the menu key opens a context menu (`src/components/context-menu.tsx`) with the same actions; with a mouse, selected items drag onto a folder tile, a tree folder or a breadcrumb to move (the drag's keys ride on `<body>` data attributes, since only sync$ handlers can accept a drop); on touch screens a long press starts selecting. The selection bar (`src/components/selection-bar.tsx`; fixed at the bottom on phones, sticky at the viewport's bottom from `sm`) shows the count and size and moves them (`useMoveSelection`, optionally into a new folder), sets the photos' visibility with one button per level (a level all of them have is pressed; making photos public or unlisted first shows the ones that change as thumbnails, like the viewer's 反映), under 情報… (a menu, also in the context menu) sets their camera and platform (`src/components/choice-picker.tsx`: the registered cameras with their first picture and なし / the platforms; the value they share is pressed, そのまま while they differ; `useBulkCamera` checks the camera exists, `useBulkPlatform`, `src/lib/db-photo-bulk.ts` reads the undo in the same batch as the update; a camera set or cleared there becomes `manual` in `metadata_source`, so the metadata reader never links one again, and the undo puts that key back as it was), their tags and shooting data (`src/components/bulk-info-dialog.tsx`, one sheet with sections: each tag the photos have, checked / mixed by how many have it, a click putting it on all then off all, new ones typed with the site's tags offered and created private; 撮影日時 (a date alone, e.g. a film roll, also sets the 撮影日時 level to date only; date, time and offset each keep the photo's own unless given), ワールド (VRChat photos), 撮影場所 (with the edit page's map, `LocationPicker`, filling the inputs) and 撮影設定, each starting at the value the photos share or empty with そのまま（写真ごと） when they differ, × clearing it; only touched fields are sent and checked with the edit page's validators, `useBulkInfo`, `src/lib/bulk-info.ts`, `setInfo` writes a row only if it is unchanged since read and returns the undo; a time taken, world or shooting settings it changes become `manual` in `metadata_source` in the same UPDATE, and a position it changes or clears `manual` in `location_source`, as on the edit page; the undo puts those keys of `metadata_source` back as they were with `json_patch`, leaving a key another edit set since, `sourcePatch`) and their public metadata levels (`src/components/bulk-metadata-dialog.tsx`, every field; a select starts at the level the photos share, or そのまま when they differ, and only changed fields are sent: `useBulkMetadata`, `src/lib/bulk-metadata.ts`, `setMetadataLevels`), and sends them to the trash (Delete too). With one item selected, touch screens get a rename icon by the count (with a mouse: F2 or the context menu). Visibility, metadata, tags and shooting data, camera and platform go 100 photos per request, one request after another, with the progress in the bar; a failure stops there and keeps the undo of what was applied. Every change has 元に戻す. `/media/trash/` lists the trash with its total size: 元に戻す puts photos back at their path (numbered `a-1.png`… if it was taken meanwhile, by a photo or a folder; refused with a message when every numbered name is taken), 完全に削除 (after a confirmation; the page sends 10 photos per request, as each costs a few B2 subrequests and a request may make 50) deletes every version of the B2 object (`src/lib/b2-delete.ts`: ListObjectVersions + DELETE per versionId, a 403 is 「削除の権限がありません」) and then the row; a file that is also a camera picture keeps its object. A failure leaves the row, so it can be retried.
- **Display path and trash** (migration `0005_path_trash.sql`): `media.file` is the B2 object key and never changes (the image Worker, the API Worker, thumbnails, og and uploads use it); `media.path` is where the admin shows the photo (folder + name; `path = file` until it is moved or renamed, a trigger fills it for inserts that leave it out). The Files tree, breadcrumbs, counts, search, list view and prev/next use `path`; the edit page shows the B2 key too when they differ. `media.trashed_at` marks the trash: trashed photos are left out of every admin list and every API Worker query (like private ones), and keep their `path` (unique only among photos not in the trash) for restoring. `LIVE_PHOTO` (`src/lib/types.ts`) is the admin's "listed photo" condition. The same migration renames `media.world` to `media.platform` (Real / VRChat; UI label "Platform"), keeping "world" for the VRChat world itself later, and drops `media.legacy_index`.
- **Public metadata and tags** (also 0005): how much of each photo's metadata the public site shows, per field and level (`src/lib/metadata.ts`, a copy of the API Worker's `workers/api/src/metadata.ts`, which applies them; a test there checks they match): ファイル名 (フォルダとファイル名 / ファイル名だけ / 出さない), 撮影日時 (秒まで … 年だけ / 出さない), カメラ (機種まで / メーカーだけ / 出さない), タグ (公開タグ / 出さない), 撮影設定 (`media.exif`, a normalized JSON object: すべて / 露出だけ / 出さない), ワールド (`media.world_id` wrld_… / `world_name`; `world_author_id` admin only: リンクまで / 名前だけ / 出さない), 撮影場所 (`media.latitude` / `longitude` / `location_source` exif or manual: 正確な位置 … 国くらい / 出さない, hidden by default). The edit page shows the last three as 撮影データ (`src/components/photo-data-fields.tsx`, `src/lib/photo-data.ts`): each value with its level select beside it and a globe / lock icon for its saved level (the globe in the public colour only when the public site really shows it: the photo is not private and the field has a value), editable under 編集. They are saved with the rest of the form, but only the groups edited since the page loaded (`photo_data_loaded`, `changedGroups`), so a page opened before the backfill cannot clear what it read. In PATCH, `exif` sets or clears (null / "") only the keys given and `world_id` / `world_name` each only when given; a changed position becomes `manual`, a changed world id drops the file's author; the original file is never touched. The world links to vrchat.com, the position to OpenStreetMap. Under the position a small map (`src/components/location-picker.tsx`; not for VRChat photos unless they already have one) sets it with a click, moves it by dragging the pin and drops it with 位置を消す: it only fills the 緯度 / 経度 inputs (input + change events, so saving makes the position `manual`) and follows them when typed, from before the map has loaded. The label 撮影設定 (not カメラ設定) keeps `getByLabel("カメラ")` unique; `media.metadata_read_at` (NULL until the original's metadata has been read) is admin only too. Originals are read on their own: an admin page, once the browser is idle and only while the tab is visible, `POST`s `/api/metadata/backfill` a batch at a time until it answers `more: false` or a call fails (`src/components/metadata-reader.tsx` in the header: a small spinner while it reads, nothing otherwise). There is no count of what is left (D1's read quota): each call is one LIMIT-ed claim through `idx_media_metadata_read_at` (0008; the live-photo condition is written `+status` / `+trashed_at` so the planner keeps to that index, checked in `backfill.spec.ts`), and once nothing is left the tab remembers it in sessionStorage per parser date (`src/lib/read-state.ts`), asking again only in a new tab, after a parser bump, an upload or ファイルの値に戻す (`markUnread`); after an error, at most once a minute. A photo waits when `metadata_read_at` is NULL, older than `PHOTO_META_PARSER_DATE` (`src/lib/photo-meta.ts`; bump it when the parser learns something, and every photo is read again, no migration), or an abandoned claim. A batch (`src/lib/backfill.ts`) claims up to 12 waiting photos atomically, in no particular order (`metadata_read_at = 'reading:<time>[!new]'`, taken again after 10 min; `!new` keeps "never read before" through it), so two tabs never read the same one; reads each original's first 128 KB (and, for a PNG with no XMP before its image data, its last 64 KB) through the image Worker's `AdminImage.bytes` (`src/lib/object-bytes.ts`; E2E binds `E2E_FAKE_B2_BYTES_URL` to the fake bucket); and writes field by field by source (migration `0008_metadata_source.sql`, `media.metadata_source`, `src/lib/metadata-source.ts`): taken-at manual > exif (DateTimeOriginal) > xmp (CreateDate) > filename (VRChat) > file_date (EXIF DateTime), exif / world / location manual > file. A reading replaces a value only from an equal or better source and never a manual one, and never clears anything; an empty location is filled only on a photo's first read (before 0008 a location cleared by hand left no mark). 0008 marks every existing value automatic, except a taken-at that was set by hand before it: on a scanner's file one that is not the file's own date, and any whose photo shows it only to the date, month or year (those become `manual`). Edits on the edit page mark the field `manual` (a cleared location too); its ファイルの値に戻す (`reset_from_file`) empties the field, drops the mark and lets the reader fill it again. A write happens only while the claim holds and `updated_at` is unchanged (an edit during the read wins). A file missing from the bucket counts as read; a photo that cannot be read or written is marked `failed:<time>` and tried again a day later, except when none of several could be read (the Worker or the login: the call fails with the reason and the claims just expire). A reset of exif or world marks the photo read long ago (waiting again), only a location reset marks it never read. Uploads set `metadata_read_at` only when the browser's parser is the current one (`parserDate`), so a stale tab's upload is read again. The E2E fixture marks every row read (far in the future), so the reader stays idle unless a test uploads an unread photo. `/setting/` sets the site defaults (`setting` row `metadata_visibility`; file names hidden, the rest as before); the edit page overrides them per photo (`media.metadata_visibility`, a JSON object) with a level select beside each field (`src/components/level-select.tsx`, also used by 撮影データ; the first option, 既定（…）, follows the site; ファイル名's sits by 場所と名前, outside the form but in it through `form=`, and a level with no control shown is sent back as it is). Tags are published one by one: `/tag/` lists every tag with its photo count and a 公開 switch (undo from the toast); a tag first used on a photo gets a private `tag` row and the toast says so; the edit page marks each tag 公開 / 非公開 (`src/lib/db-meta.ts`).
- **Fields of a tag** (migration `0010_tag_field.sql`): a tag may define fields (`tag_field`: label unique per tag, type text / number / date / select with `options`, `position`, default public level `visibility` shown / hidden; addressed by id, never reused), and every photo with the tag gets them. Values are per photo in `media.tag_values` (JSON object field id → value), the photo's own levels in `media.tag_value_visibility` (field id → shown / hidden; apart from `metadata_visibility`, which the edit page and the bulk level sheet rewrite whole). The checks (label, options, each type's value) are shared with the API Worker in `../shared/tag-field/tag-field.ts`; `src/lib/db-tag-field.ts` stores them, and each of its writes (and their undos) bumps the API's content version (`contentVersionStatement` in the write's batch, else `contentChanged`). `/tag/`: each tag's 項目 button opens its fields (`?tag=<name>` opens one): add, rename (on change), reorder (↑↓), the select's options, the default level, and remove; removing a field takes its values off every photo, after a confirmation that says how many listed photos have one, and 元に戻す puts both back with the same id. The edit page shows one group per tag with fields (`src/components/tag-field-inputs.tsx`), each input with its level (既定 follows the field) and the globe / lock like 撮影データ; only inputs edited since the page loaded are saved (`tag_fields_loaded`, `src/lib/tag-field-form.ts`), and PATCH takes `tag_values` / `tag_value_visibility` (field id → value / level, null clears, checked against the fields by `resolveTagValuePatch`; stored with `json_patch`). A tag's values stay on a photo when the tag is taken off it (they show again if it comes back). In the Files view, when the selection's photos have such a tag, the bar's 情報… menu has 「<tag>の項目…」 (「タグの項目…」 for several; `src/components/bulk-tag-field-dialog.tsx`, `src/lib/bulk-tag-field.ts`): each field starts at the value the photos with its tag share, or そのまま（写真ごと）, × clears; a value goes only to the photos with its tag (`setTagValues`, 100 per request, undo per photo). Not set by upload rules, and not embedded in the served images' EXIF.
- **Uploads** (Files view → Upload, Upload folder, or drop files/folders on the view; a folder's subfolders are created under the open one, hidden files are left out, `src/lib/drop-entries.ts` walks dropped folders; Upload folder is hidden on iOS, which cannot pick folders): the browser sends originals straight to B2; the admin only signs. Per file (`src/lib/upload-queue.ts`, pure, injected deps; `src/lib/upload-client.ts` for the browser side): bucket path = open folder + safe file name (`uploadTarget`, PNG/JPEG only), the limits of what Cloudflare Image Transformations can resize (`checkUploadLimits` in `src/lib/upload.ts`: 100 MB (decimal), 12,000 px a side, 100 MP; https://developers.cloudflare.com/images/get-started/limits/), checked in the browser before anything is sent (the size in the queue, the width and height from the PNG IHDR / JPEG SOF in `src/lib/image-size.ts`; a refused file is a skipped row with the reason) and again by `POST /api/upload` with the same words (the init carries `width` / `height`, not stored; the upload rules' orientation looks at them), SHA-256 with `crypto.subtle`, taken-at from EXIF DateTimeOriginal, else the XMP CreateDate (VRChat writes it with the real offset), else the VRChat file name, else EXIF DateTime (`src/lib/taken-at.ts`, to the millisecond, JST when no offset; a film scanner's dates, e.g. a Fuji Frontier's or a generic make "GCMC" / model "Scanner" (unset clock, 2021-01-01), are the scan's and never used, `isScanner`; its EXIF is still kept), the file's own metadata (`src/lib/photo-meta.ts`, no dependencies: JPEG/PNG EXIF for camera, lens, exposure, orientation and GPS; PNG/JPEG XMP for VRChat's `vrc:WorldID` / `WorldDisplayName` / `AuthorID` and `xmp:CreatorTool`, the last sent as `hints` for the upload rules only, not stored; fixtures in `src/lib/fixtures/` are tiny synthetic images written by Pillow), then `POST /api/upload` (stores that metadata into `exif` / `latitude` / `longitude` (`location_source` exif) / `world_*` and sets `metadata_read_at`; applies the upload rules; reserves an `uploading` row (private unless a rule says otherwise), numbering the name `a-1.jpg`… when another photo has the path; resumes the row with the same hash; answers `exists` for a hash that is already uploaded; returns the path and a presigned PUT signed over `content-type` and `x-amz-meta-sha256`, `src/lib/sigv4.ts` / `src/lib/b2.ts`), XHR PUT with progress (2–3 at a time, 3 tries with backoff, each with a fresh init), then `POST /api/upload/<id>` marks it ready only if the bucket has the object with the row's size and `x-amz-meta-sha256`. The upload key has writeFiles + listFiles + deleteFiles but no readFiles (no HEAD), so that check goes through the image Worker's `AdminImage.stat` (its read key; `src/lib/object-stat.ts`); E2E binds `E2E_FAKE_B2_STAT_URL` (loopback only) to the fake bucket instead. The image Worker with `stat` must be deployed before uploads are enabled. Uploads that never completed are listed in their folder; each page view checks each of them again on its own (the completion, 2 at a time), so a file whose PUT went through becomes a photo without uploading it again. Only the ones that still fail stay, with the reason, 「アップロードし直す」 (the same file resumes the row) and 「削除」 (`useDeleteIncomplete`). In the panel, retrying a file whose PUT succeeded only repeats the completion, and 「閉じる」 drops failed rows too (they then show as incomplete). Settings: `B2_ENDPOINT` / `B2_BUCKET` / `B2_REGION` vars and the production secrets `B2_UPLOAD_KEY_ID` / `B2_UPLOAD_APPLICATION_KEY` (`getUploadConfig`; without them the Upload button is hidden). The bucket needs a CORS rule for the S3 API: origin `https://admin.gallery.sksat.net`, operation `s3_put`, allowed headers `content-type` and `x-amz-meta-sha256`, exposed `ETag` (the web UI's presets cannot express it; set it with `b2_update_bucket`). E2E points uploads at `e2e/fake-b2.mjs` (PORT+2), which checks the signature and hash with the test key.
- **Upload rules** (`/setting/upload-rule/`, `src/lib/upload-rules.ts` pure + `src/lib/db-upload-rules.ts`): what a new photo gets is not hard-coded but an ordered list in the `setting` row `upload_rules` (a JSON array; no row = the built-in two, 「/VRChat/ フォルダ → VRChat」 and 「VRChat のファイル名 → VRChat」, old and new name formats, which reproduce the platform guess before rules). A rule matches when all its conditions do (folder and below, file name glob or a named pattern, extension, XMP CreatorTool contains, VRChat world yes/no, EXIF make/model contains, orientation after the EXIF rotation, GPS yes/no; at least one; a fact that is unknown never matches) and sets any of platform, camera, tags, visibility and metadata levels. Per field the first matching rule wins (the page says 上のルールが優先); tags add up; no match = Real, private. `POST /api/upload` reads the rules (one `setting` row, plus the rows of the cameras they name; a rule whose camera is gone sets none) and evaluates them on the requested path, so a numbered name still matches; new tags get private `tag` rows before the photo's row is made. A camera a rule sets takes the place of the one the file names (**Devices from EXIF**: no row is linked or created for it) and is recorded as `manual` in `metadata_source`, like one chosen on the edit page: a rule is a choice made in advance, so the metadata reader never replaces it. Its answer's `applied` lists what was set and by which rule, shown as chips on the panel's row (「VRChat ← /VRChat/ フォルダ」). The page saves every change at once (whole list, validated by `validateRules`; a camera must exist), with undo from the toast; the editor is a sheet (`src/components/upload-rule-editor.tsx`). 既存の写真に適用 previews a folder (one read of its photos through `idx_media_path_live`, `INDEXED BY`, since the planner otherwise picks the status or trash index and reads every photo) with counts per rule, then applies 100 photos per request with undo (both bump the API's content version in their batch). An upload a rule makes public or unlisted bumps it when it becomes ready (`completeUpload`, in the same batch); saving the rules changes nothing the API answers. Since what was set by hand is not recorded for most of these fields, it only fills in: the platform while it is Real, the camera when there is none and none was cleared by hand (then `manual`, put back by the undo), tags added, metadata levels for fields that follow the site; visibility is never changed there. CreatorTool and size are not stored, so rules on them never match photos already uploaded; world and GPS count as unknown until the original has been read (`metadata_read_at`). `/` reads every photo once. The file's facts come from the browser's parse (the admin is the only client), so a rule that makes photos public is only as sure as that parse. Rules are locked while an apply goes through (each chunk reads the saved rules); file name globs allow at most 4 `*`, so matching on the server stays cheap.
- **Digitised photos** (migration `0009_file_exif.sql`): a photo digitised from an analog original (a negative or slide, an instant photo, a glass plate, a print) has a file whose EXIF describes the scanner (or the camera on a copy stand) and whose date is the scan's. `media.exif`, `timestamp` and `camera_id` stay the shooting information; the file's own EXIF as read goes to `media.file_exif` (every file, admin only: never public, never embedded; the edit page's ファイルの EXIF), and for a scanner's file (`isScanner`: the common lab / film / flatbed scanners and any make or model with "scanner" in it, e.g. GCMC / Scanner) only there: its date is `media.digitized_at` (スキャン日時) and nothing becomes the shooting exif or taken-at. The calendars, sorting and the public taken-at use `timestamp` only; the edit page's 撮影日時 (`datetime-local` in the photo's own offset, `src/lib/taken-at-input.ts`) sets it by hand (`taken_at` → `manual`). `media.digitized_with` is the camera row it was digitised with (スキャン機材, apart from `camera_id`); `camera.kind` has `scanner` (0009 swaps the column instead of rebuilding `camera`, whose DROP would cascade to `camera_image`). Readings and uploads set it from a scanner's file (see **Devices from EXIF**). The スキャン機材 select lists scanners first; `/camera/` counts each device's スキャン photos. Public levels: スキャン機材 (`digitizer`) and スキャン日時 (`digitized_at`), both hidden by default. `media.embed_exif` (画像に EXIF を付ける: 既定 / する / しない; the default is the `setting` row `embed_exif`, set on `/setting/`) turns the served images' EXIF off for a photo. 0009 copies every stored exif into `file_exif` and, for scanners' files, moves the automatic values off (exif, and a taken-at on the scan's date); a `manual` value is never touched. The bulk sheet does not edit スキャン機材 yet.
- **Devices from EXIF** (`src/lib/device.ts`): uploads (`initUpload`) and the metadata reader (`backfillBatch`) link a photo to the device its file names: a scanner's file (`isScanner`) to `digitized_with`, any other file's shooting EXIF Make / Model to `camera_id`. The row is the one with the same manufacturer and model, case aside, as the file spells them or normalised (`normalizeDevice`: trimmed, company words such as "CORPORATION" / "IMAGING COMPANY, LTD." dropped from the make, the make dropped from the front of the model, "Canon EOS R5" → "EOS R5"; the camera table is a few dozen rows, so the lookup reads it without an index). With none, a row is created first in the same D1 batch (`ensureDeviceStatement`: the normalised names, the model as its name, the first free slug of the model (`-2`, `-3`, …), kind `scanner`, `phone` (`cameraKind`: Apple, Pixel, Galaxy, Xperia and the phone makers) or `digital`, no picture; INSERT OR IGNORE + NOT EXISTS, so two requests at once make one row). Only while the column is empty and not chosen or cleared by hand (`metadata_source.camera` / `digitized_with` = `manual`, set by the edit page when the value changes; the form sends either only when it differs from what the page loaded, `camera_loaded` / `digitized_with_loaded`, so a page opened before the reader linked one does not clear it); a camera follows the shooting EXIF as stored, so one corrected by hand names it; a VRChat photo is only linked to an existing row, never given a new one. Existing photos get theirs when the reader reads them again (the parser date was bumped for it).
- **Auth**: Production is behind Cloudflare Access, and every SSR/API request (static assets under `/build/*` etc. are served without it) is additionally checked by `src/routes/plugin@access.ts` (verifies the `Cf-Access-Jwt-Assertion` JWT against `ACCESS_TEAM_DOMAIN` / `ACCESS_AUD` in `wrangler.jsonc`; fails closed). This matters because the production `*.pages.dev` hostname is not covered by Access. The check is skipped only under `pnpm dev` (Vite) and when `ACCESS_DISABLED=1` is bound on a loopback hostname (`.dev.vars` for `pnpm serve`, `e2e/start-test-server.sh` for E2E). If you add an Access application, append its AUD tag to `ACCESS_AUD`.
- **Bindings**: D1 `DB` (metadata source of truth, see [migrations/](migrations/)). Bindings come from `wrangler.jsonc` only (Pages ignores dashboard bindings because `pages_build_output_dir` is set): top-level = production + local, `env.preview` = previews with **no D1** and only the preview Access AUD. Previews also get no B2 upload settings. Tests run against a real local D1 (sequenced via `e2e/start-test-server.sh` so wrangler dev opens the file _after_ seeding).
- **Thumbnails**: every thumbnail and preview (public or not, and camera pictures) is `/thumb/<preset>/<file>` (`src/routes/thumb/`), which calls the image Worker's `AdminImage` RPC entrypoint through the `IMAGES` service binding (`wrangler.jsonc`, production only: previews run unreviewed code, so they get neither D1 nor this binding and show placeholders), passing on the request's `Cf-Access-Jwt-Assertion`; the Worker verifies that JWT itself, so both the binding and a valid Access token are required. Responses are `Cache-Control: private`. `src/lib/images.ts` mirrors the Worker's preset list — only those presets exist, and each distinct file+preset counts toward the monthly transform quota, so do not add presets here. With `THUMBNAILS` empty (E2E sets `--binding THUMBNAILS=`) or no binding, `Thumb` renders a deterministic placeholder; the originals (up to ~37MB) are never loaded.
- **Dashboard usage cards**: 容量 adds up `media.size` of ready photos by visibility and top-level folder in one GROUP BY (`src/lib/storage.ts`; uploading rows shown apart, camera pictures not counted), with a monthly B2 cost estimate from the named price constants. Sizes there are base 1000 (`formatDecimalBytes`; the uploader's sizes and messages use `formatUploadSize`, "123.4 MB（117.7 MiB）", and its messages are Japanese). The D1 card shows the database size from that query's `meta.size_after` and, when the optional production secret `CF_ANALYTICS_API_TOKEN` (account API token, Account Analytics: Read only) is set, today's (UTC) rows read/written from the GraphQL Analytics API (`src/lib/d1-usage.ts`, account/database ids in the `CF_ACCOUNT_ID` / `D1_DATABASE_ID` vars, cached 5 min with the Cache API), all against the Free plan limits. Without the token, or on an API error, the card says so and the page still renders. アクセス reads Cloudflare Web Analytics with the same token (`src/lib/web-analytics.ts`; `rumPageloadEventsAdaptiveGroups` filtered by the `WEB_ANALYTICS_SITE_TAG` var **and** `WEB_ANALYTICS_HOST`, since the site tag covers the whole sksat.net zone, admin included): page views / visits for `?range=24h|7d|30d` (default 7d) with a per-hour/day chart, top pages, countries (country level only, named with `Intl.DisplayNames`) and referrers (the site's own hosts and Access dropped). The numbers are sampled estimates, labelled 約 / 概数. 「よく見られたページ」 is one ranking of the site's pages (`src/lib/page-ranking.ts`, `src/components/page-ranking.tsx`): the forms of a page (with or without the trailing slash) are added up over the top 1000 paths, and the top 10 are named from D1 with one IN lookup each for the photos (by `public_id`; ready, not in the trash, any visibility) and the cameras (by slug) among them. A photo row shows its thumbnail, display path and visibility icon and opens its edit page, with a link to its public page beside it (not for private ones); other pages get a name (トップ, カメラ, the camera's name, 2026年11月, 地図; else the path) and open on the public site in a new tab; a photo URL with no such photo shows its path quietly, and every old numeric `/photo/<N>` URL is one quiet 旧 URL row at the end (they map to nothing since `legacy_index` was dropped, and were never shared). Overlay views (`?photo=` on a list URL) are not counted: Web Analytics drops the query. The edit page shows the photo's 7 d / 30 d views (`src/components/photo-views.tsx`, a `server$` over the same cached answers, from the top 1000 pages). The GraphQL helpers (`src/lib/cf-graphql.ts`) share one fetch-and-cache path (Cache API, 5 min, never throws). E2E binds a test token and `E2E_FAKE_GRAPHQL_URL` (loopback only) to `e2e/fake-graphql.mjs` (PORT+3); VRT masks the dates (`[data-date]`).
- **D1 rows read** (Free plan: 5M/day, every row or index entry a query visits counts): every `<Link>` sets `prefetch="js"` (`src/lib/link-prefetch.spec.ts` checks it). Qwik City's default fetches the target page's data, i.e. runs all its loaders, whenever a Link becomes visible (again after each navigation) or is hovered, so the header's sections, the list's tiles and the edit page's prev/next ran dozens of loaders per page view. The edit page's prev/next are keyset lookups and two counts on the list's order (`neighborsStatements`, one D1 batch), served by the partial indexes of migration `0007_list_indexes.sql` (which also dropped the low-selectivity single-column indexes SQLite would otherwise pick); `neighbors.spec.ts` checks them against the old window query and checks their query plans. A new frequent query should get an index on `LIVE_PHOTO` terms written exactly as there (a partial index matches only those). D1 also counts every element of an `IN (SELECT value FROM json_each(?))` list and every index probe for it, so a lookup of many candidate names is a range instead: the upload init's duplicate and name check (`initLookups`, the requested name plus the range of its numbered names, one D1 batch; `db-upload.spec.ts` checks its decisions against the old single query and its plans) and createFolder's "anything below" (`path >= p || '/' AND path < p || '0'`). SQLite does not split an OR over a partial index, so such a lookup on `idx_media_path_live` is one statement per term. The Files view still reads every listed photo per page view: its folder tree (sizes, counts, folders) is built from all of them. `pnpm tsx scripts/bench-queries.ts [photos]` prints the hot queries' rows read on a local D1 before and after 0007, and before and after these changes.
- **No publish step**: the public site reads D1 through the API Worker (`workers/api`, read-only), which keeps its answers until the `setting` row `content_version` changes and checks it about once a minute. Every action that changes what the public API answers therefore calls `contentChanged` (`src/lib/last-good.ts`) after its write, whenever it ran (so doing it again bumps again), which gives that row a new random value (created on first use); a saved edit is live, and a hidden photo gone, within about a minute. A new action of that kind must call it too. It tries three times and then throws, so the action reports an error instead of leaving the change unseen (the API also rebuilds answers older than a day). A change already made in one D1 batch puts the bump in that batch instead (`contentVersionStatement`), as the selection's camera / platform / tags and shooting data and the camera page's カメラを外す do (`src/lib/db-photo-bulk.ts`, undos included), so both commit or neither does. The admin itself never writes to B2; it only presigns the browser's upload PUTs.

## Styling

Tailwind CSS v4 via `@tailwindcss/vite` (same setup as the root project); base styles in `src/global.css`. Use utilities only — no CSS modules or UI libraries. Shared class strings live in `src/components/ui.ts`, error/empty states use `StatePanel` (`src/components/state-panel.tsx`). Visibility has one visual language everywhere, an icon plus a label and never colour alone (`src/components/visibility-style.tsx`: public = globe, filled sky; unlisted = link, amber; private = lock, quiet zinc): `VisibilityBadge` for badges, and the same styles for the edit page's choices, the selection bar and the viewer's buttons. Phones come first: below `sm` the sections are a tab bar at the bottom (`src/components/tab-bar.tsx`; a page's own bottom bar, marked `data-bottom-bar`, replaces it, and `global.css` pads `<main>` and lifts the toast by `--bottom-ui`), the theme toggle sits in the header's menu, tap targets are at least 44px (`h-11`) and form controls use 16px text (no iOS zoom on focus; never set `maximum-scale`). Every action button is a `SubmitButton` (`src/components/submit-button.tsx`: disabled with a spinner while `action.isRunning`, the form gets `aria-busy`), and action results go to the page's `Toast` (`src/components/toast.tsx`), not inline text that can be scrolled off screen. Theme: the header toggle cycles system / light / dark, stored in `localStorage` (`admin-theme`) and mirrored on `<html data-theme>` by an inline `<head>` script before first paint (`src/lib/theme.ts`). The `dark:` variant is redefined in `global.css` to follow that attribute, and `prefers-color-scheme` when it is `system`.
